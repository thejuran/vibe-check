# Phase 3 — Collect, verify, merge, score

> **Lazy-loaded.** Read from the command spine (`commands/review.md` or `commands/deep-review.md`) when Phase 3 is entered (every review, after every Phase-2 agent has returned).
> Announce on entry, after this Read: `✓ Phase 3 — Collect, verify, merge, score`.

Scoring is performed by the deterministic-core script `scripts/score.py` (Phase 16, CORE-01/CORE-03), invoked ONCE per pass: the orchestrator collects raw facts and the agent-response set, builds one JSON envelope, pipes it to the script on stdin, and consumes the script's enriched JSON on stdout. The by-hand "apply the formula / carry-forward / dedup / threshold / silenced / in_diff override" prose has been REMOVED (D-09) — there is no longer a manual path that can produce a scored finding. **A finding has a `band`/`orchestrator_score` ONLY because the script wrote one; a finding that never went through the script has no band to render (the un-skippability that is CORE-03's point).** This wiring does NOT change scoring behavior — the script reproduces `templates/scoring.md` exactly (behavior-preserving extraction, pinned by `scripts/test_score.py`).

The orchestrator still does the work the script CANNOT (it is a pure function — no git/file/shell I/O): it collects raw facts (the per-finding `source_window`, `canonical_line_content` from the HEAD read, the `changed_line_ranges`, the `$REVIEWED_UNION` set), and it parses + dispatches.

**Git-safety gate (FIX-03, D-10/D-11/D-14) — first Bash call of Phase 3.** Run it after every Phase-2 agent has returned and, in `/deep-review`, after `30-codex-collect.md` has joined the Codex result (Codex is a separate process the hook cannot see, so the comparison must cover its run too). It compares the reviewed repo's git state with the snapshot Phase 1 took and renders one line per command the git guard refused.

```bash
GREPO=$(git rev-parse --show-toplevel 2>/dev/null)
python3 "$VC_ROOT/scripts/gitsnap.py" compare --root "$GREPO" --before "$GREPO/.turingmind/git-guard/before.json"; rc=$?
case "$rc" in
  0) python3 "$VC_ROOT/scripts/gitguard.py" notices --root "$GREPO" --consume ;;
  *) python3 "$VC_ROOT/scripts/gitguard.py" notices --root "$GREPO" --consume --repo-changed; echo "GIT STATE CHANGED DURING THE REVIEW — pass halted (rc=$rc)" ;;
esac
```

COPY every output line of that call into your reply as message text in this same turn. Text that appears only inside a Bash call's output is collapsed by the terminal and the owner never sees it — never leave a block line or a change line only in the shell output.

- **`rc` 0 — nothing halting changed.** Print each ``Blocked: <agent> tried `<cmd>` — repo untouched.`` line AND each `new tag … appeared (a tag fetch — allowed; the pass continues)` line (if any) as message text and continue to step 0 normally (D-11). No lines means no agent was refused and no tag appeared.
- **`rc` 1 or 2 — STOP the pass (D-14).** STOP the review here if ANY of these is true:
   - `gitsnap.py compare` exited 1 — the repo's HEAD, staged entries, stash, branches, moved/deleted tags, HEAD reflog or merge/rebase state changed while the agents ran;
   - `gitsnap.py compare` exited 2, or any other non-zero code — the before/after comparison could not be confirmed (missing or unreadable snapshot, git failure).

   On a STOP, print as message text one heading-free block that starts `⚠ The reviewed repo's git state changed while the review agents ran — this pass is halted.`, followed by gitsnap's change lines (on `rc` 2: `the before/after comparison could not be confirmed`), then the `Blocked: …` lines, then the sentence `This was either a review agent or you in another window — the snapshot cannot tell which.`, then the recovery hints `git stash list`, `git reflog -10`, `git status`. Then do NOT score, do NOT render findings, do NOT run Phase 4.5, do NOT enter the fix loop — persist nothing. The halt ends the review exactly like the scorer's fail-closed gate in step 5.

Tag policy: a NEW tag appearing mid-pass (e.g. `git fetch --tags`) is allowed and announced; a moved or deleted tag, any `refs/heads/*` change, or a HEAD move halts the pass. Remote-tracking refs (`refs/remotes/*`) are never compared — a fetch that only updates them neither halts nor prints.

The orchestrator does NOT assign `status`/+15 by hand — the script returns `status` (`fixed-since-last` / `persisted` / `needs-recheck`) and applies the +15 persistence modifier. **Recheck hints were ALREADY issued in Phase 2** (`20-dispatch.md` § Recheck hints) for every carried record whose agent was dispatched, and routed to one eligible reviewer for a lead whose lane was not — Phase 3 does not add hints. (The old wording placed hint construction here, after scoring; scoring runs after dispatch, so such a hint could never reach this pass's agents and the needs-recheck finding looped pass after pass.) Phase 3's job here is to COLLECT verdicts:
   - **Recheck verdicts.** From each parsed agent response (step 1) take its top-level `recheck_verdicts` array (absent ⇒ none), and for each entry build `{"source": "recheck", "token", "verdict", "reason", "agent": <the DISPATCH identity of the agent that returned it>}` — the dispatch identity OVERRIDES any self-claimed agent, the same rule step 4 applies to findings.
   - **Previous-pass fix verdicts.** Append every entry of `$FIX_VERDICTS_PREV` (bound by Phase 0.5) whose `verdict` is `obsolete` as `{"source": "fix-obsolete", "stable_hash": <its key>, "agent": "fix", "verdict": "obsolete", "at_pass", "head_sha", "reason": <the record's reason>, "verified_blob": <the record's>, "head_blob": <Phase 0.5's HEAD read, null when the file is dirty or gone>}`, and every entry whose `verdict` is `applied` (a confirmed fix of a Needs-verification item) as `{"source": "confirmed-fix", "stable_hash": <its key>, "agent": "fix", "verdict": "applied", "commit_sha": <the record's>, "at_pass", "head_sha", "reason": <the record's reason>, "verified_blob": <the record's>, "head_blob": <HEAD's blob re-read NOW, after the agents returned and the gitsnap compare passed, with the same path validation and the same two cleanliness checks as Phase 0.5; null when any fails>}`. The re-read binds the routed reviewer's verdict to the code as it stands after the verdict: an edit after the reviewer answered re-opens the item. Forward all of them, including ones whose two blobs differ — the prose never pre-filters; `score.py` decides.
   - **Collect-time blobs (`head_blobs`).** For every file named by a `$RECHECK_REQUESTS` entry that carries `snapshot_blob`, every `test_paths` entry, and every path in a carried row's `recheck_settled` `fingerprint`, read HEAD's blob re-read NOW, after the agents returned and the gitsnap compare passed, with the same path validation and the same two cleanliness checks as Phase 0.5 (`null` when any fails), into one `{<file>: <blob|null>}` object (one read per distinct path). Forward it as the envelope's `head_blobs` together with Phase 0.5's `$TOUCHED_PATHS` as `touched_paths` — the prose never pre-filters; `score.py` decides.

   The orchestrator does NOT decide whether a verdict resolves anything — `score.py` applies the token/agent/carried/needs-recheck guard and returns accepted resolutions in `resolved[]`; rejected verdicts appear in `filtered[]` with a `verdict: …` reason (`verdict: malformed`, `verdict: unrequested token`, `verdict: agent not asked`, `verdict: record not carried`, `verdict: record not needs-recheck`, `verdict: contradicted by still-applies` — two agents disagree, so the record stays open —, `verdict: stale fix verdict`, `verdict: evidence changed since verification`, `verdict: confirmed fix on a non-needs-verification record`, `verdict: confirmed fix awaiting independent re-check: no eligible reviewer this pass`, `verdict: confirmed fix awaiting independent re-check: the routed reviewer gave no verdict`, `verdict: confirmed fix not verified: the routed reviewer says it still applies`, `verdict: confirmed fix not verified: the reviewed code is not the repaired code`, `verdict: routed re-check without a confirmed fix`, `verdict: fix not yet confirmed: no eligible reviewer ran this pass`, `verdict: fix not yet confirmed: the routed reviewer gave no verdict`, `verdict: fix not confirmed: the routed reviewer says it still applies`, `verdict: fix not confirmed: the reviewed code is not the code at HEAD`, `verdict: fix not confirmed: no change near the finding or in its file since it was raised`, `verdict: fix not confirmed: a reviewer said it still applies and the code is unchanged since`, `verdict: fix not confirmed: no change to this Needs-verification item's file or tests since it was raised; it stays open for your decision`, `verdict: confirmed fix not verified: the routed reviewer said it still applies and the code is unchanged since`), and the finding stays open. A plain `resolved` on a persisted record closes only through the bound plain rule (matching `snapshot_blob`, a change since it was raised); an independent-route `resolved` closes only from the routed reviewer with a matching blob. A confirmed-fix verdict never resolves alone: score.py resolves the item (source `confirmed-fix`) only with the routed reviewer's `resolved` from `$RECHECK_REQUESTS` (`20-dispatch.md` step 3).

   **`members[]` (H-LANE, v2.10 Wave 1 — per-member carry-forward evidence).** When a `$CARRYFORWARD` finding carries a `members[]` array, each entry is a FULL finding record (the same input fields as any finding: `file`, `line`, `title`, `current_code`, `source_window`, …). Do for every entry EXACTLY what the two paragraphs above do for the finding, IN THE SAME HEAD read of that file (the members sit within ±2 lines of the finding — do NOT add a second read tool): compute the canonical line content at `member.file:member.line` (strip trailing whitespace) and set it as that member's `canonical_line_content` (null/absent when the file:line is gone), AND resolve that member's `canonical_window` (its line plus its next ≤2 non-blank HEAD lines, trailing-whitespace-stripped, joined with `\n`; null/absent when the line is gone) and set it on the member entry. The script carries EVERY member as a finding in its own right on this pass through the identical carry-forward path: each member's status (`persisted` / `needs-recheck` / `fixed-since-last`) comes from ITS OWN `canonical_line_content` and `canonical_window` (null/absent canonical → that member is `fixed-since-last`, never invented; the window disambiguates a low-entropy line such as `}` exactly as for a finding) and it is scored on its own facts (its own `source_window`, line, confidence), so a member survives, is silenced or drops sub-threshold independently of the row's lead — a lead that was fixed or suppressed does not take its members with it; a member's stored `current_code` is the write-time snippet it is compared against — never overwrite it. Fresh `findings[]` carry no `members` (the script strips any such key at ingress).

   **`canonical_window` (ROBUST-03 — additive, carry-forward STATUS only).** IN THE SAME HEAD read (do NOT add a second read tool), the orchestrator ALSO resolves a small surrounding window — `canonical_window` = the line at `finding.file:finding.line` PLUS its next ≤2 non-blank HEAD lines, each trailing-whitespace-stripped (the SAME posture as `canonical_line_content`), joined with `\n`. Pass it on the carryforward entry alongside `canonical_line_content`. When the file:line is gone, `canonical_window` is null/absent exactly like `canonical_line_content` (the script reads the null canonical as `fixed-since-last` first, so the window is never consulted in that case). **`canonical_window` is consumed ONLY by the script's carry-forward STATUS compare** (it disambiguates a low-entropy first line such as `}` or `);` by the surrounding context) and **NEVER feeds `stable_hash`** — the hash path still keys on the single-line `canonical_line_content` (D-07; the frozen golden digest does not move). This is purely additive: it does NOT change the single-line `canonical_line_content` the hash path reads. Note explicitly: the script only WIDENS the compare when BOTH the stored snippet AND this window have ≥2 non-blank lines — so a **single-line offending snippet is compared on its first line only (no churn)** even though this resolved window may include a following HEAD line; a legal `current_code="}"` against an unchanged HEAD therefore stays `persisted`, never flipping to `needs-recheck`.

   **Carried Needs-verification records (Phase 53, D-12/O-2 — relocation by content, NV only).** For each `$CARRYFORWARD` entry whose `band` is `needs-verification`, IN THE SAME HEAD read of its file (do NOT add a second read tool), the orchestrator locates the item by its recorded code before computing `canonical_line_content`, instead of reading the stored `line` blindly. Compare lines with BOTH sides `.strip()`ped — the lane's snippet may be dedented. The "stored first line" is the first non-blank line of the entry's stored `current_code`.
   1. If the HEAD line at the stored `line` still equals the stored first line, use it as for any carried finding.
   2. Otherwise search the file for lines equal to the stored first line. When exactly one match exists, OR one match is nearest unique to the stored `line` (no other match at the same distance), set the carryforward entry's `line` to that line number and compute `canonical_line_content` there (the HEAD line, trailing whitespace stripped). Also set the same `line` on the `$RECHECK_REQUESTS` entry whose `stable_hash` is this record's: the script matches a lane's verdict to the record by file, line, agent and title, so a relocated record whose request still names the old line would reject the verdict as `verdict: record not carried`.
   3. When two or more matches tie for nearest, keep the stored `line` and pass the HEAD line found there as `canonical_line_content` — the script sees the changed evidence and reports `needs-recheck` ("code changed", O-2); ambiguity is never stability.
   4. When NO match exists in the file, or the file is gone, pass `canonical_line_content` and `canonical_window` as null/absent exactly as for an ordinary finding. **For a needs-verification record this is NOT a closure — it is never fixed-since-last: the script keeps the record open as `needs-recheck` under its stored identity (a carried NV row keeps its stored `stable_hash` verbatim, so an owner's earlier call stays attached to it and is re-asked on the changed evidence), and the item closes only when the lane that raised it answers the recheck hint `resolved` with named evidence (the script lists that resolution in `resolved[]`), when a Confirm → fix verdict obsoletes it, or when the owner decides it — never because the text could not be found (a rename, a reformat or a move to another file can preserve the failure).**

   **Needs-verification evidence fingerprint.** For every LOCATED needs-verification record (cases 1-3), `canonical_window` is NOT the ordinary ≤2-line window: it is the located line PLUS the following non-blank HEAD lines up to the stored snippet's non-blank line count — N non-blank lines in the stored `current_code` give N non-blank HEAD lines, each with trailing whitespace stripped and leading indentation kept, blank lines skipped, joined with `\n` (a one-line snippet gives a one-line window). The script compares the WHOLE stored snippet against this window (`_nv_carry_status`) and reports `persisted` — no recheck requested, the owner's earlier call kept — ONLY when that evidence fingerprint is confirmed unchanged. A changed body under an unchanged first line is `needs-recheck` ("code changed"): the script refreshes the row's `current_code` to the window and the owner's earlier call on the item is re-asked at Finalize — a call is never silently kept on changed evidence. When the stored `current_code` is empty there is nothing to confirm: pass the window anyway and the script reports `needs-recheck` (an unconfirmed item is rechecked before any closure). Never pass any stored text as `canonical_line_content` or `canonical_window` — both are always HEAD text or null.

   **Symbol-anchored Needs-verification records.** For an entry whose `line` is null and whose `needs_verification.symbol` is non-empty, case 1 does not apply (there is no stored line). Cases 2, 4 and the evidence fingerprint apply with a UNIQUE match only: two or more matches of the stored first line is a tie with no stored line to fall back to, so pass `canonical_line_content` AND `canonical_window` as null exactly as in case 4. `line` stays null on the entry (the row is addressed by its symbol in the report and in the recheck hint). The symbol text is NEVER searched to decide anything about the record — a surviving name is not evidence (a function can keep its name while its body changes materially, or survive only as a call site; only the recorded snippet confirmed at HEAD is evidence). An unlocated or changed symbol-anchored record is therefore `needs-recheck` under its stored identity, never closed by the orchestrator, and the raising lane rechecks the named failure.

   Why: an unrelated insertion above an item must not falsely trigger a recheck or re-ask a recorded "wired in Phase N" deferral (D-12). The relocation supplies the correct canonical and window for the item's own code; the carried row's identity is its stored `stable_hash`, which the script keeps verbatim regardless. Only an edit to the item's own recorded code, a failed relocation or a band change is new evidence. This rule applies to Needs-verification records and, per the next paragraph, to decided records only — undecided ordinary findings keep the stored-line read and the ≤2-line window above (general relocation is out of scope).

   **Carried decided records (Phase 57, D-01 — relocation by content for decided records).** For each `$CARRYFORWARD` entry whose `stable_hash` is in `$DECIDED_HASHES`, and for each of its `members[]` carrying an `obligation` whose `obligation.stable_hash` is in `$DECIDED_HASHES`, when the record's band is not `needs-verification` (a Needs-verification record already follows the block above), IN THE SAME HEAD read of its file apply cases 1, 2 and 3 above with one change: the "stored first line" is the record's stored `canonical_line_content` (an ordinary record is hashed on it) — for an entry its own stored `canonical_line_content`; for a member its `obligation.snapshot.canonical_line_content`, else the first non-blank line of its stored `current_code`. Compare with BOTH sides `.strip()`ped. Case 2 sets the entry's (or member's) `line` to the match and computes `canonical_line_content` and `canonical_window` there, and also sets the same `line` on the `$RECHECK_REQUESTS` entry whose `stable_hash` is this record's (a request still naming the old line would be rejected as `verdict: record not carried`). The lead's own member record moves with the lead: a `members[]` entry with no `obligation` and the same `agent`, `file`, `title` and stored `line` as the entry gets the entry's relocated `line` and is read there — left at the stored line it would come back as a phantom extra row of whatever code now sits there. Case 3 (a tie for nearest) keeps the stored `line`. Case 4 (no match in the file) reads the stored `line` as for any ordinary finding — a null canonical stays `fixed-since-last` for an ordinary record (unlike a Needs-verification record).

   Why: the canonical text is unchanged, so `score.py` recomputes the SAME `stable_hash` and the owner's decision stays attached across a pure line shift (D-01). An edit within 5 lines above or below the line (D-14) is reported by `score.py` as `snapshot.nearby_at` and re-asks the decision (D-02) — the prose does not detect that. The helper, not the prose, decides which records are decided (`$DECIDED_HASHES`, bound in Phase 0.5). An undecided ordinary row keeps the stored-line read; general relocation stays out of scope.

2. **Raw-fact collection the script CONSUMES (the script DECIDES; the orchestrator SUPPLIES).** For each finding, attach the raw facts the script needs to recompute the orchestrator-verified booleans (it overrides the agent's self-reported `in_diff` / `silenced_marker_nearby` per `templates/agent-output-schema.md` hard rule #4):
   - **changed-line ranges** — pass `changed_line_ranges` (`{file: [[start,end],…]}`) in the envelope; the script recomputes `in_diff` as a pure range test (the `+20 if in_diff` term fires from THIS, not from an agent claim). The ranges are built ONLY from each hunk's `+` and `-` body lines, by `scripts/diff_ranges.py`; the orchestrator must never read the ranges from hunk headers, because the unchanged context lines git prints around an edit are display, not change. The helper's contract: an added or replaced block gives its new-side lines. A hunk that only deletes (header `+T,0` under `-U0`; inside a context hunk, a run of `-` lines with no `+` lines) has no new-side lines; it gives `[max(T, 1), T + 1]`, the two new-side lines on either side of the deletion point, so a deleted guard directly above or below a flagged line counts as a nearby change. A replace block that removes more lines than it adds also covers the one new-side line just after it, for the same reason (D-02). These ranges feed the D-14 re-check trigger (`_nearby_changed`): they are the same ranges `score.py` uses for `in_diff` and `snapshot.nearby_at`.

     **Coordinate contract.** Findings and ranges share one line space per route: the new side of the range-source diff. On the default route that is the working tree as it is on disk — `git diff HEAD` already contains every staged change in working-tree line numbers. Build the ranges from exactly one range source per route (below), never from a concatenation of diffs that number lines in different files (HEAD, index, working tree, or each commit of a series). Every git call here carries `--no-color --no-ext-diff --no-textconv --no-relative --src-prefix=a/ --dst-prefix=b/`, so a repo-local color, prefix, external-diff, textconv or relative-path setting cannot change the text the helper reads; a blank context line printed empty (`diff.suppressBlankEmpty`) is read as context by the helper.

     | Route | Range source |
     |-------|--------------|
     | default (mode 1), pass 1 | `git diff --no-color --no-ext-diff --no-textconv --no-relative --src-prefix=a/ --dst-prefix=b/ HEAD` alone — the `git diff --staged` section reviewers also receive is a second view of the same changes in index line numbers and is never appended to the range source |
     | GSD (mode 4), pass 1 | `git diff --no-color --no-ext-diff --no-textconv --no-relative --src-prefix=a/ --dst-prefix=b/ "<phase-start-sha>"` — `<phase-start-sha>` is the literal printed after `PHASE_START=` by the 00-scope.md phase-range fence (which halts on anything that is not a commit id); substitute it; when that printed value is empty use `HEAD` — one diff, commit vs working tree |
     | default or GSD, pass ≥ 2 | `git diff --no-color --no-ext-diff --no-textconv --no-relative --src-prefix=a/ --dst-prefix=b/ "<last-reviewed-sha>"` — `<last-reviewed-sha>` is the literal printed after `LAST_REVIEWED_SHA=` by the 05-state.md step-2 fence (`carry_state.py last-head-sha`, which prints only a validated commit id); substitute it; never copy `head_sha` from the state JSON — one diff, last reviewed commit vs working tree |
     | range (mode 3) | `git diff --no-color --no-ext-diff --no-textconv --no-relative --src-prefix=a/ --dst-prefix=b/ <range>` |
     | PR (mode 2) | `gh pr diff <ref> --color never` — the cumulative diff; never `--patch`, which emits a commit series that numbers each hunk in that commit's own file (the helper refuses a series) |
     | `--all` (mode 5) | no diff; pass `changed_line_ranges = {}` and skip the fence |

     The revision in the GSD and pass ≥ 2 rows is a literal the agent substitutes — a shell variable does not survive into a separate Bash call. Only a value printed after `PHASE_START=` or `LAST_REVIEWED_SHA=` by those fences is ever substituted: both fences refuse anything that is not a 40- or 64-hex commit id, so a crafted value cannot reach this command — double quotes stop word-splitting, not `$(...)`, so they are not the protection. The quotes still make an empty or unsubstituted placeholder fail (git rejects an empty revision, and `set -o pipefail` turns that into the halt below) instead of silently diffing the index against the working tree.

     Pipe the route's range source into the helper in ONE Bash call, substituting the row above for `<range source>`:
     ```bash
     set -o pipefail
     if RANGES_JSON=$(<range source> | python3 "$VC_ROOT/scripts/diff_ranges.py"); then
       printf '%s\n' "$RANGES_JSON"
     else
       echo "Review halted — the changed lines could not be read from the diff; nothing was scored." >&2
       exit 1
     fi
     ```
     The printed JSON is `changed_line_ranges`. A non-zero exit halts this pass: do not score, and never fall back to `{}` or to ranges read by hand (fail closed — a pass scored with missing ranges silently drops the in-diff term). The helper also refuses colored or non-diff text with a fixed reason (exit 2), so `{}` is printed only for a genuinely empty diff. An empty diff prints `{}` and is not a failure.

Carry the printed literal to Phase 4.5, which records it as the pass entry's `reviewed_tree`. `NEARBY_LINE_RANGES=<json>` is the exact changed-line ranges between what the LAST pass recorded and what this pass reviews, in the same line numbers as `changed_line_ranges`; when it is non-empty, pass it verbatim as the envelope's `nearby_line_ranges` (even `{}`, which means nothing changed).
