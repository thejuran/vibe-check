Skips on the runner (D-20, owner ruling). Two groups of tests in the existing suite skip themselves on GitHub's Linux machines through their own built-in conditions: the replay test that skips in a linked worktree without the private recordings, and lane-archive tests that skip on Linux. The owner allows these, pinned by test id with each reason. Planner rulings (technical, with rationale):

- Where the ids come from. `pytest -rs` prints a skip as `file:line: reason` and folds skips raised at the same line into one row, so it cannot give test ids (checked on pytest 9.0.3 on 2026-11-13). Test ids and reasons are read from pytest's built-in `--junitxml` result file, where every skipped test is a `testcase` element with `classname`, `name` and a `skipped` child whose `message` is the reason. `-rs` stays in the suite command for the readable log only.
- Test id form. A `testcase` with `classname="plugins.vibe-check.scripts.<module>.<Class>"` and `name="<test>"` is the id `plugins/vibe-check/scripts/<module>.py::<Class>::<test>`, the same form as the five ids above. A skipped `testcase` whose `classname` does not start with `plugins.vibe-check.scripts.` cannot be on the list (this phase's own tests never skip) and is reported with its raw `classname::name`.
- Where the list lives. `RECORDED_SKIPS` in `left_out_guard.py`: `None` means "not yet recorded"; a tuple of `(test id, reason)` pairs, possibly empty, means "recorded".
- Bootstrapping order (record, pin, then call green). D-20 says the list is taken from the real runner's first run, so this plan ships `RECORDED_SKIPS = None`. In that state `check-skips` always exits 1 with `SKIP LIST NOT YET RECORDED — THIS IS A RECORDING RUN, NOT A GREEN RUN — STOPPING` after printing every skip it saw. The first run on the runner is therefore red by design at the skip guard step and is never counted as a green run. Plan 62-08 copies the printed set into `RECORDED_SKIPS` (only if every entry belongs to the two approved groups; anything else goes back to the owner), and only a later run on that pinned commit can be called green.
- What the list may hold. Only ids starting `plugins/vibe-check/scripts/test_replay.py::` or `plugins/vibe-check/scripts/test_lanearchive.py::`, and never one of the five left-out ids. Each entry's reason must also be, character for character, the one skip reason its file carries, held in the constant `APPROVED_SKIP_REASONS`: for `test_replay.py`, `Phase-40 transcripts are local-only (gitignored); a linked worktree has none to recover from` (the `skipIf` at line 281; two adjacent string literals that Python joins into this one string); for `test_lanearchive.py`, `no sandbox temp root on this machine` (the `skipTest` at line 416). These are the only two skip reasons in those two files at 2.14.1, and pytest 9.0.3 writes each into the result file's `message` attribute as the bare string (checked by the planner on 2026-11-14 with a two-test sample). This is checked by a test on the constant, so a later edit cannot quietly add a skip from another file or for another reason, and matching a skip to an approved group at pin time is a mechanical check, not a judgment (D-20).
- The guard adds no skip itself. It only compares. No skip, deselect or ignore is added anywhere beyond the D-18 five.

Both scripts are run by CI as `python3 -I <script>`. Isolated mode does not put the script's folder on `sys.path`, so each script is a single file with no sibling imports.

House conventions (62-PATTERNS.md): `unittest.TestCase`; `sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))` then the sibling import with `# noqa: E402`; `REPO_ROOT = os.path.abspath(os.path.join(HERE, "..", ".."))`; exit codes 0 clean / 1 violation / 2 usage or unusable input; refusal messages in caps ending `— STOPPING`; every `subprocess.run` has a `timeout`; temp dirs via `tempfile.mkdtemp()` with `self.addCleanup(shutil.rmtree, tmp, True)`; a `TestImportSet` class per module; every mutant asserts the mutation really happened (`assertIn` on the original needle, `assertNotEqual(mutant, original)`).

Environment: the Bash tool runs zsh, so multi-line shell goes in `bash -s <<'BASH' … BASH`. Use bare `pytest`, never `python3 -m pytest` or `python3 -m unittest`. Run commands from the repository root of the checkout you are working in. Nothing under `plugins/` may change.
