Planner rulings (technical, with rationale):

- Pinning: the driver materialises `plugins/vibe-check` at `BASELINE_COMMIT` into a temp directory with `git archive` and uses that copy as `VC_ROOT`, as the source of the fence text and as the source of the fixtures. Rationale: the record must keep re-deriving after Phase 63 changes the working tree.
- Process isolation: nothing from the pinned tree is imported into the Python process. Helper calls and state preparation go through subprocesses (`python3 <pinned scripts dir>/<helper>.py …`, or `python3 -I -c` with the pinned scripts directory inserted into `sys.path` inside that child). Rationale: CI runs this test in the same pytest process as the plugin's own tests, which import the working-tree copies of `carry_state`, `finalize_gate` and `batch_card` under the same module names.
- What is fingerprinted: per step, the exit code and the normalised standard output; the gate decision JSON; the stop sentence shown to the owner (or its absence); the `batch_card.py decisions-report` JSON (the deterministic report text; REVIEW.md prose itself is written by the model); the names of files written and archived relative to the situation's work directory; whether the state file ended up closed. Standard error is recorded only as present or absent. Rationale: error text from system tools differs between the Mac's BSD tools and Linux's GNU tools and is not plugin behaviour; the owner-visible output is.
- Fence definition, the same as the step-counting rule in plan 62-03: the house definition from `test_finalize_card.bash_fences`, indented fences included, the one four-backtick fence included. The pinned `90-finalize.md` holds 18 bash fences; the fences that print `BLOBFILE` and `GATEFILE` are indented. A column-0-only reader would find about half (9 openers start in column 0) and lose them.
- Step tally per situation (recorded, not part of pass/fail), counting the same kinds of thing the static rule in plan 62-03 counts: `commands_run` (every fence the driver executes and every inline command it runs in the model's place, counted each time it runs), `values_carried` (printed paths pasted into a later fence or inline command), `writes` (files written in the model's place). The static count is over the instructions; this tally is over one walk, so a retry can run a fence twice.

House conventions (62-PATTERNS.md): stdlib only; `TestImportSet`; every `subprocess.run` with a `timeout`; exit codes 0 ok / 1 difference / 2 unusable input; temp resources released on every path (`try/finally` in the CLI, `addCleanup` in tests); every mutant asserts the mutation happened; fixtures are asserted to contain what the test assumes. New basenames must not repeat any basename under `plugins/vibe-check/scripts` or `.github/scripts`. Bare `pytest`; multi-line shell in `bash -s <<'BASH' … BASH`. Nothing under `plugins/` may change.
