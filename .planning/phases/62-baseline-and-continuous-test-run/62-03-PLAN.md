What a bash fence is (the house definition, the same one `test_finalize_card.bash_fences` uses: indented fences included). A fence opens on a line that is optional leading whitespace, then three or four backticks, then `bash`, then end of line. It closes on the next line that is optional leading whitespace followed by the same number of backticks and nothing else. Measured at `dd8e4ab` by the plan checker and re-measured by the planner on 2026-11-13, per file in `MODE_PATHS["finalize"]` order: `commands/review.md` 1, `phases/shared/00-contract.md` 0, `phases/shared/01-bootstrap.md` 1, `phases/review/00-scope.md` 10, `phases/review/05-state.md` 7, `phases/review/06-config.md` 5, `phases/shared/90-finalize.md` 18; total 42. A rule that only sees fences starting in column 0 finds 18 of the 42 and misses, among others, the fences that print `BLOBFILE`, `GATEFILE`, `DECFILE` and `SUBSETFILE`; that rule is wrong and one mutant in this plan exists to prove the script does not use it.

Planner rulings (technical, with rationale):

- The four-backtick fence. `90-finalize.md` holds one fence that opens with four backticks and `bash` (the archive step, near line 331 at 2.14.1). It counts as one fence: it is a command the model runs, and the existing archive tests execute it. It is one of the 18.
- Inline commands. Some commands the model must run are written in the running text, not in a fence, for example `rm -f "$SUGGESTFILE" "$REFSFILE" "$RESOLVEFILE"` near line 272 of `90-finalize.md` at 2.14.1. They count: D-05 counts commands the model runs, wherever they are written. The planner's scan at `dd8e4ab` found five candidate spans in `90-finalize.md` (near lines 180, 184, 243, 271, 272) and none in the other six files. Task 2 classifies each candidate by hand as "instructs a run" or "mention only" and fixes the lead-in list so the script counts exactly the first kind.

The counts:

- `bash_fences`: number of fences as defined above. Each is one command the model runs.
- `inline_commands`: number of inline code spans (single backticks, on one line, outside every fence of any language) that (1) start with a lowercase command word followed by a space, (2) hold at least one `"$NAME"` or `"$NAME.` for a printed name, and (3) are immediately preceded by one of the lead-ins in `INLINE_RUN_LEADS`. Each is one command the model runs.
- `write_tool_writes`: number of occurrences, anywhere in the file, of a phrase in `WRITE_PHRASES`. Each is one file the model writes with the Write tool. The phrase list is fixed in the script and justified line by line in CRITERION.md.
- `carried_paste_sites`: for each name NAME that some bash fence prints with a line of the form `printf 'NAME=%s\n' "$..."` (NAME matching `[A-Z_]+FILE`), the number of occurrences of `"$NAME"` or `"$NAME.` in bash fences other than the fence that prints NAME, plus the occurrences inside counted inline commands. Each is one value the model copies from earlier output into a later command.
- `printed_literals_distinct`: number of distinct printed names (eleven in `90-finalize.md` at 2.14.1, `BLOBFILE` and `GATEFILE` among them). Reported, but not added to the total, because every copy of a printed value is already counted as a paste site.
- `model_run_steps` = `bash_fences` + `inline_commands` + `write_tool_writes` + `carried_paste_sites`. This single number is measure (b) of D-01.

The count is static over the declared path, so like the byte figure it is an upper bound: a given Finalize run does not execute every fence.

Where the file list comes from. At capture the script takes the seven files from `footprint.MODE_PATHS["finalize"]` and writes them into the record. Every later check (the standing test here, `verify_baseline` in plan 62-07, Phase 63's comparison of the baseline side) recounts the files named in the record, not the live `MODE_PATHS`. Rationale: Phase 63 may change that list; the 2.14.1 baseline must not move when it does. The test also pins the seven paths as a constant, so the record's own list cannot be shortened unnoticed.
